# Unsupported DDL Features

This file documents Spanner DDL features that cannot be fully supported due to
limitations in memefish (the SQL parser) or the INFORMATION_SCHEMA model.

## Unsupported or AST-only surfaces

These features either lack a corresponding memefish AST node or cannot be
recovered from the available live metadata. Each subsection states the exact
boundary.

### `GRANT USAGE ON SCHEMA` — AST-only live recovery

`GRANT USAGE ON SCHEMA [DEFAULT|<schema_name>[, ...]] TO ROLE <role>` now
round-trips through `FromDDLStatements` / `ToDDLStatements`. The grant is
stored in `Schema.SchemaGrants` as an AST-only construct because the emulator
does not expose a corresponding `INFORMATION_SCHEMA` table for schema-level
usage grants; recovery from `INFORMATION_SCHEMA` alone is not yet supported.
Supported `REVOKE USAGE ON SCHEMA` statements remove only the matching AST-only
grant.

### Model grants

`INFORMATION_SCHEMA.ROLE_MODEL_GRANTS` can describe privileges on models, but
memefish v0.8.1 has no model-privilege AST node. `ToDDLStatements` therefore
returns an explicit error when `RoleModelGrants` is non-empty; it never omits
these grants from generated DDL.

### Sequence grants — AST-only live recovery

memefish v0.8.1 parses and generates both exact sequence grants and schema-wide
sequence grants:

```sql
GRANT { SELECT | UPDATE }
   ON SEQUENCE sequence_list | ON ALL SEQUENCES IN SCHEMA schema_name [, ...]
   TO ROLE role_list
```

`astconv` preserves them in `Schema.SequenceGrants` and
`Schema.AllSchemaGrants`, including matching `REVOKE` behavior. A 2026-07-23
real-Spanner probe accepted both forms and returned an exact sequence grant
from `GetDatabaseDdl`.

Production INFORMATION_SCHEMA currently exposes `SEQUENCES` and
`SEQUENCE_OPTIONS`, but no role-sequence-grant table. `LoadSchema` therefore
cannot recover these grants from live metadata alone. In the probe, a grant on
all sequences in an empty schema was accepted but did not appear in the
subsequent `GetDatabaseDdl` response. When the schema contained a sequence,
`GetDatabaseDdl` expanded the wildcard into an exact
`GRANT ... ON SEQUENCE schema.sequence` statement rather than preserving the
original schema-wide grant intent.

### `PLACEMENT KEY` — AST-only live recovery

memefish v0.8.1 adds `ast.ColumnDef.PlacementKey`, and `astconv` preserves the
modifier in `Schema.PlacementKeyColumns` for AST-originated round trips:

```sql
CREATE TABLE Singers (
  SingerId INT64 NOT NULL,
  Location STRING(MAX) NOT NULL PLACEMENT KEY
) PRIMARY KEY (SingerId);
```

Production `INFORMATION_SCHEMA.COLUMNS` currently has no placement-key
attribute, so `LoadSchema` cannot reconstruct it. A 2026-07-23 real-Spanner
probe reached semantic/configuration validation (`InvalidArgument` without a
`Syntax error:` marker), confirming that the service parser accepts the syntax;
the configured instance did not allow the table to be created.

### Scalar-expression indexes — live metadata, no memefish AST

Managed Spanner and the pinned Spanner Omni runtime accepted GoogleSQL index
keys containing scalar expressions in a 2026-08-28 probe. The documented
spelling wraps an expression in an extra pair of parentheses, and ordinary
column keys can precede an expression key in the same index:

```sql
CREATE INDEX VenuesByCity
ON Venues((JSON_VALUE(VenueData.address.city)));

CREATE INDEX VenuesByNameState
ON Venues(VenueName, (JSON_VALUE(VenueData.address.state)));
```

`INFORMATION_SCHEMA.INDEX_COLUMNS` retains the scalar text in `EXPRESSION`
and exposes an internal `_ExpressionIndex_<index>_<position>` value in
`COLUMN_NAME`. That internal name is not a table column and must not be emitted
as user DDL. memefish v0.8.1 has no index-expression AST node, so
`ToDDLStatements` returns an explicit error whenever an index key has a
non-NULL `EXPRESSION`.

The pinned Cloud Spanner Emulator rejects the documented expression-key form
as a syntax error. Current managed Spanner and Omni also reject `DESC` after a
GoogleSQL expression key even though the DDL grammar displays an ordering
suffix. A non-deterministic key such as `CURRENT_TIMESTAMP()` reaches semantic
validation and is rejected as non-deterministic. These runtime observations
are probes, not a promise that the boundaries are stable. See the
[expression-index observation](../knowledge/observations/spanner-expression-indexes.md)
for the retained environment and plan evidence.

## Resolved parser surfaces wired in `astconv`

### Tables without an explicit primary key and zero-column primary keys

Spanner treats these two forms differently:

```sql
CREATE TABLE Pkless (Name STRING(MAX))
```

The omitted clause creates a hidden `rowid INT64 NOT NULL GENERATED BY DEFAULT
AS IDENTITY (BIT_REVERSED_POSITIVE) HIDDEN` primary key. By contrast,
`PRIMARY KEY ()` creates a zero-column key and therefore a singleton table.
Managed Spanner and Spanner Omni `2026.r2.1-beta` produced the same DDL,
metadata, and insert behavior in a 2026-08-24 probe. Cloud Spanner Emulator
v1.5.56 does not implement omission: it rejects the statement with `Must
specify either table or column PRIMARY KEY`.

`astconv` preserves omission for AST-only round trips. Live metadata naturally
contains the expanded hidden identity column and ordinary primary-key rows,
which are reconstructed as explicit DDL. The converter recognizes the live
`IDENTITY_KIND` value `BIT_REVERSED_POSITIVE_SEQUENCE` as the
`BIT_REVERSED_POSITIVE` identity parameter.

A zero-column key has a `TABLE_CONSTRAINTS` primary-key row but no
`KEY_COLUMN_USAGE` or `INDEX_COLUMNS` rows. Managed Spanner and Omni also omit
`INDEXES`; Emulator v1.5.56 instead exposes one `INDEXES.PRIMARY_KEY` row.
`astconv` accepts both metadata shapes and emits the service-equivalent
table-constraint form:

```sql
CREATE TABLE Singleton (
  Name STRING(MAX),
  PRIMARY KEY ()
)
```

Managed Spanner, Omni, and Emulator v1.5.56 accept this form and canonicalize it
to trailing `PRIMARY KEY()`. This representation works around two memefish
v0.8.1 edges:
the trailing form parses but its unparser drops an empty key list, while the
table-constraint AST unparses correctly even though the parser does not accept
an empty key list in that position.

### memefish v0.8.1

- `PLACEMENT KEY` in column definitions
- `GRANT` / `REVOKE {SELECT|UPDATE} ON SEQUENCE`
- `GRANT` / `REVOKE {SELECT|UPDATE} ON ALL SEQUENCES IN SCHEMA`

The live-recovery limits for these features are documented above.

### memefish v0.8.0

### Anonymous table constraint style `PRIMARY KEY`

`fromCreateTable` now handles `*ast.TablePrimaryKey`, so statements like

```sql
CREATE TABLE t (
  a INT64,
  b INT64,
  PRIMARY KEY (a, b)
);
```

round-trip without losing the primary key. `toCreateTable` emits non-empty keys
in the trailing `) PRIMARY KEY (...)` form, which matches `GetDatabaseDdl`
output; the zero-column compatibility form is the exception documented above.

### `GRANT ... ON ALL ... IN SCHEMA`

`fromGrant` / `toRolesDDL` now support:

- `GRANT {SELECT|INSERT|UPDATE|DELETE} ON ALL TABLES IN SCHEMA <schema> TO ROLE <role>`
- `GRANT SELECT ON ALL CHANGE STREAMS IN SCHEMA <schema> TO ROLE <role>`
- `GRANT SELECT ON ALL VIEWS IN SCHEMA <schema> TO ROLE <role>`

They are stored as AST-only constructs in `Schema.AllSchemaGrants`.
The corresponding `REVOKE` forms are also handled. They remove matching
table/view/change-stream/schema usage/role-membership grants from the schema
representation and do not broaden or remove unrelated grants.

## Partially Supported

### `CREATE PROPERTY GRAPH`

Default-schema property graphs are now reconstructed from
`PROPERTY_GRAPHS.PROPERTY_GRAPH_METADATA_JSON`, and `astconv` also serializes
`CREATE PROPERTY GRAPH` ASTs back into the same metadata model for round-trip
tests.

Rows with non-empty `PROPERTY_GRAPH_SCHEMA` / `baseSchemaName` cannot be
reconstructed faithfully because current memefish property graph AST nodes only
accept unqualified graph names and element table names. Current Spanner named
schema documentation does not list property graphs as a supported named-schema
object, so this remains fail-closed metadata handling rather than an active
local implementation target.

### `CREATE TABLE ... OPTIONS` — resolved

Table-level options (e.g. `OPTIONS(locality_group='...')`) now round-trip through
`FromDDLStatements` / `ToDDLStatements`. The options are stored in a `TableOptions`
slice on `Schema`.

`INFORMATION_SCHEMA.TABLE_OPTIONS` is now populated on real Spanner, so
`cmd/roundtrip` reads it and can reconstruct table-level `OPTIONS(...)` clauses
when building DDL from INFORMATION_SCHEMA. The emulator does not yet expose
`TABLE_OPTIONS`, so this recovery does not work on the emulator.

### Generic database, table, and index options

The converters preserve generic option names, types, and values rather than
enumerating a fixed allowlist. This includes custom full-text dictionary table
options, `columnar_policy` on database/table/index objects, and database
schema-drop-protection options.

A 2026-08-25 managed-Spanner probe returned these live `TABLE_OPTIONS` shapes:

- `fulltext_dictionary_table`: `BOOL`, value `TRUE`
- `fulltext_dictionary_staleness`: `STRING`, value `5s`
- table `columnar_policy`: `STRING`, value `disabled`

Spanner Omni `2026.r2.1-beta` returned the same rows. Both environments retained
all three temporary objects' option clauses in `GetDatabaseDdl`, but returned no
`INDEX_OPTIONS` row for an index with `columnar_policy = 'disabled'`. Therefore
AST-originated index options round-trip, while `LoadSchema` cannot recover that
index option from the currently available live metadata.

The managed database had no rows for the three selected database-level options,
and the probe deliberately did not mutate shared database settings. Their
configured live types and explicit SQL `NULL` behavior consequently remain
unverified; absence is preserved as omission rather than materializing a
default.

Emulator v1.5.56 accepted table `columnar_policy = 'disabled'` but omitted it
from `GetDatabaseDdl`, exposes neither `TABLE_OPTIONS` nor `INDEX_OPTIONS`,
rejected `fulltext_dictionary_staleness`, and rejected index
`columnar_policy`. These are emulator compatibility limits, not converter
allowlist restrictions.

### `GRANT SELECT ON VIEW` distinction — resolved

`ROLE_TABLE_GRANTS` contains both table and view grants. `toRolesDDL` now
cross-references the `Views` list to emit `GRANT SELECT ON VIEW` for views
and `GRANT ... ON TABLE` for tables, matching `GetDatabaseDdl` output.

### `ON UPDATE (expr)` for columns — resolved

memefish supports `ON UPDATE (expr)` in column definitions and related
`ALTER COLUMN` forms (`ast.OnUpdate`, `ast.AlterColumnSetOnUpdate`,
`ast.AlterColumnDropOnUpdate`), and this repository now round-trips the
schema-state form exposed through `INFORMATION_SCHEMA.COLUMNS.ON_UPDATE_EXPRESSION`
for `CREATE TABLE` columns as well.

## Named Schema Support by DDL Family

Spanner supports named schemas (created with `CREATE SCHEMA`). This repository
now preserves qualified identity for every locally representable named-schema
family listed by the current
[Spanner named-schema documentation](https://cloud.google.com/spanner/docs/schema-and-data-model#named_schemas)
and for named-schema scalar functions verified by a real-Spanner probe. Other
families remain fail-closed rather than silently emitting a leaf object name or
omitting an object.

| DDL family | Current status | Exact boundary |
|---|---|---|
| `CREATE SCHEMA` | Supported | Emitted from `INFORMATION_SCHEMA.SCHEMATA` (default and system schemas are skipped). |
| `CREATE TABLE` | Supported | Table names, columns, constraints, options, placement-key AST state, foreign-key targets, and dependency ordering retain qualified identity. Interleave parents and synonyms must be in the table's schema; cross-schema foreign keys are supported. |
| `CREATE INDEX` / `CREATE SEARCH INDEX` | Partial | Non-interleaved indexes are supported and the index/base-table schemas must match. A 2026-07-26 raw-DDL probe confirmed that emulator v1.5.55 and real Spanner accept a qualified regular-index `INTERLEAVE IN` target. memefish v0.8.1 represents that target with an unqualified `ast.Ident`, and the representable unqualified form resolves in the emulator's default schema rather than the named index schema. Regular and search indexes therefore fail closed in both directions when named-schema interleave metadata is present. |
| `CREATE VIEW` | Supported | `TABLE_SCHEMA` is preserved in both AST directions and in grant classification. |
| `CREATE SEQUENCE` | Supported | `SEQUENCE_SCHEMA` is preserved in sequences, options, and exact grants. |
| `CREATE FUNCTION` | Supported | A 2026-07-26 real-Spanner probe accepted a named scalar function and preserved both `ROUTINE_SCHEMA` and `SPECIFIC_SCHEMA`. Routine, parameter, option, and exact table-function-grant identities are qualified. |
| `GRANT` / `REVOKE` | Partial | Qualified path-backed targets are supported for tables, views, sequences, change streams, and table functions, including schema-isolated revoke behavior. Schema-wide forms are also supported. Model grants remain upstream-blocked because memefish has no model-privilege node. |
| `CREATE PROTO BUNDLE` | Supported metadata handling | The DDL is database-scoped and proto type names are fully qualified. Non-empty descriptor payloads from every `SCHEMATA` row are decoded, unioned, deduplicated, and sorted. A 2026-07-26 real probe observed the payload only on the default-schema row, including after creating a named schema; multi-row union behavior is therefore locally tested but not currently exercised by the service. |

### DDL families outside the documented named-schema surface

The current named-schema support list does not include vector indexes, change
streams, models, property graphs, placements, locality groups, or statistics
packages. Placement-based geo-partitioning explicitly disallows named schemas.
Do not open upstream memefish work solely because these nodes use `ast.Ident`.
First establish service support with current documentation or a bounded probe;
if support is added, their identifier-only AST fields would then need path
support. Default-schema conversion for these families remains supported as
described elsewhere in this file.

## Notes on Spanner Routines

### No `CREATE PROCEDURE` in Spanner

Spanner does **not** support user-defined `CREATE PROCEDURE`. The only
callable procedures are system procedures (e.g., `CALL cancel_query(...)`).
INFORMATION_SCHEMA.ROUTINES stores UDFs, not procedures.

### `CREATE FUNCTION` (SQL UDF)

SQL UDFs are not yet documented in the official DDL reference but are
already GA and used in production (e.g., 80 MySQL-compatible functions
via https://github.com/googleapis/spanner-sql-udf).

Syntax used in practice:
```sql
CREATE [OR REPLACE] FUNCTION [schema.]name(params) RETURNS type AS (expr)
```

Remote UDFs (Preview) use additional clauses:
```sql
CREATE FUNCTION name(params) RETURNS type
[NOT] DETERMINISTIC LANGUAGE REMOTE
OPTIONS (endpoint = '...', max_batching_rows = N)
```

Both are supported by memefish's `ast.CreateFunction` and this project's
`astconv` package for AST-originated round trips. Live `ROUTINES` rows do not
always preserve the syntax mode needed to reconstruct a remote UDF. The
converter also checks `ROUTINE_OPTIONS` for language and determinism metadata,
but when neither that fallback nor AST-only metadata is available it returns an
explicit error instead of guessing a remote-function form.

A bounded 2026-07-26 real-Spanner probe also confirmed that a schema-qualified
scalar SQL UDF is accepted and that its routine/specific schema metadata is
preserved. The probe removed the temporary function and schema afterward.

## Not Applicable for DDL Generation

These INFORMATION_SCHEMA tables contain metadata but do not correspond to
DDL statements:

- `*_PRIVILEGES` tables — show effective permissions, not DDL
- `COLUMN_COLUMN_USAGE` — tracks generated column dependencies
- `SPANNER_STATISTICS` — handled via `ALTER STATISTICS`
